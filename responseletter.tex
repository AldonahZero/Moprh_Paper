\section*{Replies to Metareview}

\metareviewcomment{1} Correct the description of SEDAR's comment-before-mutation and restore-after-mutation mechanism. Clearly explain the actual methodological differences between MORPH and SEDAR, avoiding misleading characterizations of the latter.

\reply
We have revised the description of \sedar{} and the motivating example in Sections~I (Introduction), II (Background and Motivation), and VI (Related Work), and we have clarified the methodological differences between \tool{} and \sedar{} in Sections~II (Background and Motivation) and~VI (Related Work).

\textit{Description of \sedar{}.} \sedar{} translates each statement with the source-side sub-schema referenced by that statement. During mutation, it temporarily comments out fragments that the downstream fuzzer cannot parse and restores them before execution. However, the commented-out fragments are not mutated, and a fragment with a translation error still fails on the target DBMS after restoration. In addition, later statements are translated without the target-side schema and types produced by the translation of preceding statements. Figure~1 below shows both limitations on a test case transferred by \sedar{} from \textsc{PostgreSQL} to DuckDB. \sedar{} translates \texttt{MONEY} in S1 to \texttt{DECIMAL(18,2)}, but S2$'$ keeps the money literal \texttt{\textquotesingle{}\$12.50\textquotesingle{}}, which DuckDB cannot convert to \texttt{DECIMAL}. In S3$'$, the \texttt{to\_date} fragment is commented out during mutation and restored before execution, and still fails because DuckDB does not provide \texttt{to\_date}.

\par\smallskip\noindent\begin{minipage}{\linewidth}\centering
\includegraphics[width=0.6\linewidth]{media/motivating_rc3.pdf}

{\footnotesize Figure 1: Motivating example of running \sedar{} on a \textsc{PostgreSQL} seed (Left): S2$'$ is inconsistent with the target-side type in S1$'$, and the incompatible fragment in S3$'$ is commented out during mutation and restored before execution, leaving the translation error unrepaired. \tool{} abstracts dialect-specific logic via AQT and instantiates it with the target-side context in the target dialect (Right).}
\end{minipage}\par\medskip

\textit{Differences in \tool{}.} \tool{} addresses both limitations before mutation. First, it repairs incompatible fragments using parser and execution feedback. Thus, fragments that \sedar{} comments out during mutation are translated into target-compatible SQL and remain available for mutation. Second, the AQT records forward read-after-write dependencies and the cumulative schema context of the source test case, and \tool{} updates the target-side schema and type context after each translated statement, so later statements are instantiated against the translated target-side state. In Figure~1, \tool{} uses the type of \texttt{amt} in S1$'$ to instantiate the literal in S2$'$ as \texttt{12.50}, and instantiates $<$\texttt{StrToTimestamp}$>$ in S3$'$ with \texttt{strptime}, so all statements execute on DuckDB.


\textit{Experimental results.} The evaluation in Section~IV (Evaluation) shows the effect of these differences. Compared with \sedar{}, \tool{} achieves 5\%--19\% higher syntactic correctness and 100\%--272\% higher execution validity across the four target DBMSs (Table~IV), and retains 22\%--113\% more functions, up to 62\% more data types, and 23\%--146\% more keywords in the transferred seeds (Table~V), as summarized in the table below. In 24-hour fuzzing campaigns, \tool{} covers 14\% more branches (Figure~7) and detects 16 more bugs than \sedar{}.

\metareviewcomment{2}
Moderate the novelty claims and better distinguish MORPH from existing SQL translation approaches, particularly SEDAR, RISE, QTRAN, and CrackSQL. Explain more concretely what AQT and its associated mechanisms contribute beyond existing techniques, especially in the context of DBMS fuzzing.

\reply
We have revised Sections~I (Introduction), II (Background and Motivation), III (Approach), and VI (Related Work) to clarify how \tool{} differs from existing approaches, including query migration approaches (CrackSQL and RISE), oracle transfer approaches (QTRAN), and fuzzing seed transfer approaches (\sedar{}). Below, we compare these approaches with \tool{} in terms of their goals, challenges, methods, and experimental results.

\textit{Different goals.} CrackSQL and RISE target query migration: they translate one self-contained query or procedural artifact at a time and aim to produce an equivalent target query. QTRAN targets oracle transfer: it translates a query and regenerates its target-side mutant so that the metamorphic relation is preserved for logic-bug detection. \sedar{} and \tool{} share the goal of transferring existing test cases into fuzzing seeds. For this goal, a transferred seed must execute on the target DBMS, retain testing-relevant SQL structures, and remain parsable and mutable by the downstream fuzzer.

\textit{Different challenges.} For CrackSQL and RISE, the main challenge is to map the dialect-specific functions, types, and syntax of a single query or procedural artifact to an equivalent target form. For QTRAN, the main challenge is to keep the metamorphic relation between a query and its mutant valid after translation. For \sedar{}, the main challenge is to make transferred test cases executable on the target DBMS and parsable by the downstream fuzzer, which it addresses by translating each statement with its referenced source-side sub-schema and temporarily commenting out incompatible fragments during mutation. For \tool{}, the main challenge is that SQL logic is tightly coupled with dialect-specific syntax, which requires separating syntactic differences while preserving the structure, cross-statement dependencies, and semantic richness of a test case.

\textit{Different methods.} CrackSQL combines functionality-based query processing, cross-dialect syntax embedding with contrastive learning, and local-to-global translation. RISE reduces a complex query or procedural artifact to a simpler form, learns the local dialect rewrite from the reduced form, and applies the rewrite back to the original artifact. QTRAN uses dialect knowledge and retrieval to translate a query and regenerate its target-side mutant. \sedar{} uses an LLM to translate each statement under its referenced source-side sub-schema, and temporarily comments out parser-incompatible fragments during mutation and restores them before execution. In contrast, \tool{} represents each source test case as an AQT that records normalized statement structures, cross-statement dependencies, and schema context, and instantiates it under the target dialect while propagating the translated target-side context across statements. We have updated Table~I and Sections~II (Background and Motivation) and~VI (Related Work) to reflect these differences.

\textit{Different results.} As a result, across the four target DBMSs, \tool{} achieves 7\%--528\% higher branch coverage and detects 5--22 more bugs than the six evaluated fuzzing tools in 24-hour campaigns, including 14\% higher coverage and 16 more bugs than \sedar{}. It also improves execution validity by 100\%--450\% over the translation baselines.

\metareviewcomment{3} Clarify how MORPH differs from and complements SmartFuzz in seed construction. The additional comparison is useful but limited in its experimental scope. The revision should acknowledge these limitations and avoid overstating comparative advantages.

\reply
We have clarified how \tool{} differs from SmartFuzz in Section~VI (Related Work), and extended the comparison in Section~IV (Evaluation). In terms of goal, SmartFuzz generates new DBMS-specific seeds, whereas \tool{} transfers existing test cases across DBMSs. In terms of methodology, SmartFuzz extracts SQL features from the official documentation of the target DBMS and bug-relevant features from historical crash-triggering inputs, and prompts an LLM with combinations of these features to generate seeds. In contrast, \tool{} uses cross-statement dependencies and cumulative schema and type context to translate and repair existing test cases.

To compare them under the same setting, we use the seeds released by SmartFuzz and run them with \griffin{} on all four target DBMSs, with the same DBMS versions, resource allocation, campaign duration, and coverage measurement as the other tools in RQ2. As shown in Figure~7 and Table~III below, \tool{} covers 7\% more branches and detects 5 more bugs than SmartFuzz. On MonetDB, DuckDB, and ClickHouse, \tool{} achieves higher coverage than SmartFuzz throughout the campaign. This advantage stems from the smaller dialect gaps. On Virtuoso, whose dialect differs most from the source DBMSs (the lowest execution validity of \tool{} in Table~IV), \tool{} grows coverage more slowly at the beginning of the campaign, since it transfers seeds across a larger dialect gap, whereas SmartFuzz generates seeds directly for the target DBMS. \tool{} nevertheless reaches coverage close to that of SmartFuzz by the end of the 24-hour campaign (40,183 vs. 40,773 branches), which shows the effectiveness of the transfer.

\reviewquestion{1.2} What independent benefit does the dependency graph provide beyond context propagation?

\reply
The dependency graph guides context selection during instantiation and repair. Without it, \tool{} lacks explicit links for selecting dependency-relevant statements and object-state summaries for prompting. For example, in \texttt{ALTER TABLE t ADD COLUMN b INT; SELECT b FROM t;}, the edge selects the schema update for the translation and repair of the \texttt{SELECT}. Summaries provide the content, while edges guide the selection.

To isolate this benefit, we have added an ablation study in Section~IV (Evaluation). We compare four context-selection modes under the same LLM, knowledge base, source corpus, repair budget, and statement order: (1) \tool{}, which selects predecessors through the dependency graph; (2) $\tool{}_{\textit{win}}$, which replaces dependency-based selection with the five most recent successfully translated statements while keeping the same object summaries, so that it differs from \tool{} only in whether the dependency graph is used; (3) $\tool{}_{\textit{all}}$, which provides all preceding successfully translated statements together with the complete source-side and target-side context; and (4) $\tool{}_{\textit{w/o-ctx}}$, which selects the same predecessors as \tool{} but provides only their source-side statements, without their translated target-side statements or target-side object-state summaries. We measure execution validity at the statement level, the number of predecessors provided per statement, the proportion of predecessors that are dependency-relevant (i.e., connected to the current statement by a dependency edge), and input tokens per statement.

\tool{} achieves higher execution validity than $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$ (0.716 vs. 0.599 and 0.643), while reducing input tokens per statement by 11.9\% and 72.3\%, respectively. In $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$, only 22.6\% and 4.2\% of the provided predecessors are dependency-relevant. In addition, 15.4\% of statements select dependency predecessors outside the five most recent statements, which a recency-based window cannot capture. The context of $\tool{}_{\textit{all}}$ grows with test-case length: on test cases with more than 20 statements, its input tokens per statement are 4.98$\times$ those of \tool{}. These results show that the independent benefit of the dependency graph lies in selecting a compact, dependency-relevant context whose size does not grow with test-case length, while achieving higher execution validity than larger contexts.

\reviewquestion{1.3} How were CrackSQL, RISE, and SEDAR adapted and configured for the four target DBMSs, and how did the authors ensure a fair comparison?

\reply
We have added the configuration of the translation baselines in Section~IV (Evaluation). Each baseline follows its original translation workflow. SQLGlot and jOOQ use their built-in dialect support. CrackSQL and RISE use the official SQL documentation of each target DBMS as dialect knowledge, i.e., the \href{https://www.monetdb.org/documentation-Aug2024/user-guide/sql-summary/}{MonetDB SQL Reference}, the \href{https://docs.openlinksw.com/virtuoso/}{Virtuoso Documentation}, the \href{https://duckdb.org/docs/sql/introduction}{DuckDB SQL Documentation}, and the \href{https://clickhouse.com/docs/sql-reference}{ClickHouse SQL Reference}. Since CrackSQL and RISE are designed to translate one query or artifact at a time, we translate the statements of each test case individually and reassemble them in their original order, without schema context. \sedar{} requires no additional dialect knowledge; we run the original \sedar{} binary obtained from its authors, which translates complete test cases using the extracted source schemas as context.

To ensure a fair comparison, all methods transfer the same collected source test files, and no method receives additional manually written translation rules. The transferred seeds of all methods are evaluated on the same target DBMS versions (MonetDB v11.51, Virtuoso v7.2, DuckDB v1.4.3, and ClickHouse v24.8 LTS) with the same measurement of syntactic correctness and execution validity. In fuzzing, all compared methods run for 24 hours with the same DBMS versions, resource allocation, and coverage measurement, and the results are averaged over five independent runs. The prompts and configurations of all baselines are included in our \href{https://anonymous.4open.science/r/MorphArtifact-8E44/}{artifact}.

\reviewcomment{1.4} It is therefore unclear what ($G_{tc}$) contributes independently beyond recording the dependencies and preserving an order that is already present. \reply
We have revised Section~III (Approach) to make the role of the dependency graph explicit: it selects the dependency-relevant context used in the instantiation and repair of each statement. We have revised Algorithm~2 accordingly and added an ablation study in Section~IV (Evaluation) that isolates this role from context propagation.

\textit{Role of the dependency graph.} For each statement, the new \textsc{SelectContext} step follows the dependency edges to select the preceding statements that write the objects it reads, and provides their source and translated statements in the prompts for instantiation and repair. This gives the LLM the schema changes that the statement depends on, even when they occur far back, without unrelated statements. Accordingly, the graph selects only dependency-relevant predecessors (100\% for the dependency graph, 22.6\% for the five-statement recency window, and 4.2\% for the full context), captures the 15.4\% of statements whose dependencies lie beyond the window, uses 11.9\% fewer input tokens per statement than the five-statement recency window and 72.3\% fewer than the full context, and achieves the highest execution validity (0.716 for the dependency graph, 0.599 for the five-statement recency window, and 0.643 for the full context). Details can be found in \questionref{1.2}.

\textit{Revision of Algorithm~2.} The main change is the new \textsc{SelectContext} step (Line~4), which selects the dependency-relevant context $C_t^{(i)}$ for each statement, and \textsc{InstantiateStmt} now uses $C_t^{(i)}$ instead of the full target context $C_t$. In addition, since forward read-after-write dependencies always point from earlier to later statements, the original statement order already satisfies them, and we have removed the stable topological sort. The revised Algorithm~2 is shown below, with removed parts in red and added parts in blue.

\textit{Difference and advantage.} \tool{} performs pre-migration repair to make seeds parser-compatible, whereas \sedar{} defers some compatibility handling until after mutation: it temporarily comments out fragments that the fuzzer cannot parse during mutation and restores them before execution. \reviewcomment{3.4} Missing related work: SQLRight (USENIX Sec 2022) absent from RQ2; sqllogictest is never discussed; classic seed-selection literature ignored.

\reply
We have added SQLRight as a baseline in RQ2. Since SQLRight officially supports only SQLite, PostgreSQL, and MySQL, we have adapted it to the four target DBMSs while keeping its AFL-based queue scheduling, AST-based mutator, and oracle framework, and we have included the adaptation code in our \href{https://anonymous.4open.science/r/MorphArtifact-8E44/}{artifact}. We have also extended the related work in Section~VI (Related Work) with SQLRight, sqllogictest, and seed-selection techniques. SQLRight performs coverage-guided DBMS fuzzing for logic bugs, whereas \tool{} constructs initial seeds for DBMS fuzzers. sqllogictest validates query results across database engines with a shared test format, whereas \tool{} transfers test cases into seeds for coverage-guided fuzzing. Seed-selection and scheduling techniques, such as corpus minimization and power schedules (e.g., AFLFast), choose or prioritize seeds within an existing corpus, whereas \tool{} constructs the initial corpus for target DBMSs that lack one; the two directions are therefore orthogonal and can be combined.

\reviewcomment{3.5} What's novel here is the conjunction of approaches: AST abstraction + RAG + parser-feedback repair, which are established ideas assembled around the AQT.

\reply
We have clarified in Section~VI (Related Work) that \tool{} adopts these techniques but focuses on maintaining evolving target-side context across an ordered test sequence through the AQT. Specifically, the AQT records forward read-after-write dependencies and cumulative schema context, which \tool{} uses to select dependency-relevant context and to propagate the translated target-side state across statements during instantiation and repair. We have also added an ablation study in Section~IV (Evaluation) that isolates the contributions of the dependency graph and context propagation. As shown in Table~VI below, dependency-based context selection achieves higher execution validity than a recency-based window and the full context (0.716 vs.\ 0.599 and 0.643) while using 11.9\% and 72.3\% fewer input tokens per statement, and providing only the source-side statements of the same predecessors reduces execution validity to 0.523. Details can be found in \metareviewref{2}.
