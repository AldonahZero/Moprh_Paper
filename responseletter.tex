\section*{Replies to Metareview}

\metareviewcomment{1} Correct the description of SEDAR's comment-before-mutation and restore-after-mutation mechanism. Clearly explain the actual methodological differences between MORPH and SEDAR, avoiding misleading characterizations of the latter.

\reply
We have revised the description of \sedar{} in Sections~I, II, and VI to accurately reflect its mutation-handling mechanism. Specifically, \sedar{} temporarily comments out fragments incompatible with the downstream fuzzer's parser during mutation and restores them before executing the mutated SQL on the target DBMS. This mechanism does not permanently remove the original query logic. We have also revised the motivating example in Section~II to distinguish the intermediate representation used during mutation from the SQL executed by the target DBMS.

We have clarified the methodological differences between \tool{} and \sedar{} in Sections~II and~VI. \sedar{} translates statements individually using their referenced source-side sub-schemas, while \tool{} uses the AQT to propagate evolving target-side schema and type context across statements. In addition, \tool{} uses parser and execution feedback to repair incompatibilities before mutation, whereas \sedar{}'s comment-and-restore mechanism primarily addresses compatibility with the downstream fuzzer during mutation.

We have added a controlled comparison in Section~IV to evaluate the two mutation-handling strategies. For each of the four target DBMSs, we applied both strategies to the same 300 translated seeds and ran \griffin{} for 24 hours in five independent repetitions. Compared with \sedar{}'s strategy, \tool{}'s strategy achieves 27.2\%, 15.5\%, 4.0\%, and 9.4\% higher branch coverage on DuckDB, MonetDB, Virtuoso, and ClickHouse, respectively.

\metareviewcomment{2}
Moderate the novelty claims and better distinguish MORPH from existing SQL translation approaches, particularly SEDAR, RISE, QTRAN, and CrackSQL. Explain more concretely what AQT and its associated mechanisms contribute beyond existing techniques, especially in the context of DBMS fuzzing.

\reply
We have revised Sections~I, II, III, and VI so that \tool{} is no longer positioned as the first whole-test-case transfer framework or the first approach that adapts transferred seeds to downstream fuzzers. We have also clarified that \tool{} builds on established techniques such as structural decomposition, localized translation, and dialect-aware retrieval, and that its contribution lies in coordinating them across an ordered test sequence through AQT. We have revised the related work in Section~VI to distinguish \tool{} from \sedar{}, CrackSQL, RISE, and QTRAN in terms of goals, challenges, methods, and results.

\textbf{Different goals.} CrackSQL and RISE target query migration: they translate one self-contained query or procedural artifact at a time and aim to produce an equivalent target query. QTRAN targets oracle transfer: it translates a query and regenerates its target-side mutant so that the metamorphic relation is preserved for logic-bug detection. \sedar{} and \tool{} share the goal of transferring existing test cases into fuzzing seeds. For this goal, a transferred seed must execute on the target DBMS, retain testing-relevant SQL structures, and remain parsable and mutable by the downstream fuzzer.

\textbf{Different challenges.} A fuzzing seed is an ordered sequence of independently executed statements, and later statements may depend on the target-side state produced by earlier statements. For example, in \texttt{ALTER TABLE t ADD COLUMN b INT; SELECT b FROM t;}, the \texttt{SELECT} is valid only if the translated \texttt{ALTER TABLE} has produced the expected column on the target DBMS. When the target dialect changes a type, a constraint, or a DDL form, subsequent statements must follow the translated target state rather than the source state. Translating each statement correctly in isolation is therefore insufficient. Our focus is on maintaining this evolving target-side context across an ordered test sequence, beyond translating a self-contained query or preserving an oracle relation. \sedar{} addresses the same setting but translates each statement using a source-side sub-schema and does not maintain translated target-side context across statements.

\textbf{Different methods.} AQT is built on a standard SQL AST; its contribution is not the tree representation itself but the cross-statement information it adds and how this information is consumed during transfer. First, AQT records forward read-after-write dependency edges between statements. These edges identify dependency-relevant preceding statements for context selection during instantiation and repair, while the original statement order is retained. Second, AQT records the cumulative schema context of the source test case, including object-state summaries such as object existence, table definitions, column names and types, constraints, and DDL-induced schema changes. During instantiation, \tool{} maintains the corresponding target-side context and updates it after each translated statement. Each statement is thus instantiated and repaired against the translated target state. Third, abstract labels separate dialect-specific constructs from the surrounding structure, so that dialect-aware instantiation remains local while the original structure is preserved. Finally, \tool{} uses parser and execution feedback to repair transferred seeds before mutation, whereas \sedar{} temporarily comments out parser-incompatible fragments during mutation and restores them afterward. As described in their papers, the workflows of CrackSQL, RISE, and QTRAN do not propagate target-side context across the statements of a test case. We have updated Table~I and Sections~II and~VI to reflect these differences.

\textbf{Different results.} The evaluation in Section~IV provides evidence for the practical value of this design. Disabling cross-statement context propagation reduces execution validity from 0.661 to 0.523, supporting the contribution of target-side context propagation. Replacing dependency-based context selection with a recency-based window or the full context reduces execution validity to 0.599 and 0.643, respectively, while increasing input tokens (\commentref{1.2}). At the system level, \tool{} improves execution validity by 130\% and branch coverage by 14\% over \sedar{}, and the controlled mutation-handling comparison is described in \metareviewref{1}.

% Source: Reviewer A, Question 2.
\reviewcomment{1.2} What independent benefit does the dependency graph provide beyond context propagation?

\reply
Context propagation maintains the target-side state of the test case, while the dependency graph determines which preceding statements are provided as context for the current statement. For each statement, \tool{} uses $\Delta$ to select its direct predecessors, i.e., the preceding statements that write objects read by the current statement, keeps only the most recent one for each set of shared objects, and provides their source and translated statements in the prompts for instantiation and repair. For example, in \texttt{ALTER TABLE t ADD COLUMN b INT; SELECT b FROM t;}, the dependency edge selects the \texttt{ALTER TABLE} statement as context when translating and repairing the \texttt{SELECT}, regardless of how many unrelated statements appear between them.

To isolate this benefit, we have added an ablation study in Section~IV. We compare four context-selection modes under the same LLM, knowledge base, source corpus, repair budget, and statement order: (1) \tool{}, which selects dependency predecessors through $\Delta$; (2) $\tool{}_{\textit{win}}$, which replaces dependency-based selection with the five most recent successfully translated statements while keeping the same object summaries, so that it differs from \tool{} only in whether the dependency graph is used; (3) $\tool{}_{\textit{all}}$, which provides all preceding successfully translated statements together with the complete source-side and target-side context; and (4) $\tool{}_{\textit{w/o-ctx}}$, which disables target-side context propagation. We measure execution validity at the test-case level, the number of predecessor statements provided per statement, the proportion of provided predecessors that are dependency-relevant (i.e., connected to the current statement in $\Delta$), and input tokens per statement.

As shown in the table, \tool{} achieves higher execution validity than $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$ (0.661 vs. 0.599 and 0.643), while reducing input tokens per statement by 11.9\% and 72.3\%, respectively. In $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$, only 22.6\% and 4.2\% of the provided predecessors are dependency-relevant. In addition, 15.4\% of statements select dependency predecessors outside the five most recent statements, which a recency-based window cannot capture. The context of $\tool{}_{\textit{all}}$ grows with test-case length: on test cases with more than 20 statements, its input tokens per statement are 4.98$\times$ those of \tool{}. These results show that the independent benefit of the dependency graph lies in selecting a compact, dependency-relevant context whose size does not grow with test-case length, while achieving higher execution validity than larger contexts.
