\section*{Replies to Metareview}

\metareviewcomment{1} Correct the description of SEDAR's comment-before-mutation and restore-after-mutation mechanism. Clearly explain the actual methodological differences between MORPH and SEDAR, avoiding misleading characterizations of the latter.

\reply
We have revised the description of \sedar{} in Sections~I (Introduction), II (Background and Motivation), and VI (Related Work) to accurately reflect its mutation-handling mechanism. Specifically, \sedar{} temporarily comments out fragments incompatible with the downstream fuzzer's parser during mutation and restores them before executing the mutated SQL on the target DBMS. This mechanism does not permanently remove the original query logic. We have also revised the motivating example in Section~II (Background and Motivation) to distinguish the intermediate representation used during mutation from the SQL executed by the target DBMS.

We have clarified the methodological differences between \tool{} and \sedar{} in Sections~II (Background and Motivation) and~VI (Related Work). \sedar{} translates statements individually using their referenced source-side sub-schemas, while \tool{} uses the AQT to propagate evolving target-side schema and type context across statements. In addition, \tool{} uses parser and execution feedback to repair incompatibilities before mutation, whereas \sedar{}'s comment-and-restore mechanism primarily addresses compatibility with the downstream fuzzer during mutation.

We have also evaluated whether the transferred seeds preserve the behavior of the source test cases. On 100 randomly sampled MySQL-to-DuckDB test cases, \tool{} achieves the highest result and state equivalence (52.0\% and 74.0\%), compared with 38.0\% and 69.0\% for \sedar{}, as shown in the table below.

\metareviewcomment{2}
Moderate the novelty claims and better distinguish MORPH from existing SQL translation approaches, particularly SEDAR, RISE, QTRAN, and CrackSQL. Explain more concretely what AQT and its associated mechanisms contribute beyond existing techniques, especially in the context of DBMS fuzzing.

\reply
We have revised Sections~I (Introduction), II (Background and Motivation), III (Approach), and VI (Related Work) to clarify how \tool{} relates to existing whole-test-case transfer and fuzzer-oriented seed adaptation approaches, in particular \sedar{}. We have revised the related work in Section~VI (Related Work) to state that \tool{} adopts related techniques, including structural decomposition, localized translation, and dialect-aware retrieval, but targets fuzzing seed transfer, and to distinguish \tool{} from \sedar{}, CrackSQL, RISE, and QTRAN in terms of goals, challenges, methods, and results.

\textbf{Different goals.} CrackSQL and RISE target query migration: they translate one self-contained query or procedural artifact at a time and aim to produce an equivalent target query. QTRAN targets oracle transfer: it translates a query and regenerates its target-side mutant so that the metamorphic relation is preserved for logic-bug detection. \sedar{} and \tool{} share the goal of transferring existing test cases into fuzzing seeds. For this goal, a transferred seed must execute on the target DBMS, retain testing-relevant SQL structures, and remain parsable and mutable by the downstream fuzzer.

\textbf{Different challenges.} For CrackSQL and RISE, the main challenge is to map the dialect-specific functions, types, and syntax of a single query or procedural artifact to an equivalent target form. For QTRAN, the main challenge is to keep the metamorphic relation between a query and its mutant valid after translation. For \sedar{}, the main challenge is to make transferred test cases executable on the target DBMS and parsable by the downstream fuzzer, which it addresses by translating each statement with its referenced source-side sub-schema and temporarily commenting out incompatible fragments during mutation. For \tool{}, the main challenge is that SQL logic is tightly coupled with dialect-specific syntax, which requires separating syntactic differences while preserving the structure, cross-statement dependencies, and semantic richness of a test case.

\textbf{Different methods.} CrackSQL combines functionality-based query processing, cross-dialect syntax embedding with contrastive learning, and local-to-global translation. RISE reduces a complex query or procedural artifact to a simpler form, learns the local dialect rewrite from the reduced form, and applies the rewrite back to the original artifact. QTRAN uses dialect knowledge and retrieval to translate a query and regenerate its target-side mutant. \sedar{} uses an LLM to translate each statement under its referenced source-side sub-schema, and temporarily comments out parser-incompatible fragments during mutation and restores them afterward. \tool{} builds an AQT that adds cross-statement information consumed during transfer. First, AQT records forward read-after-write dependency edges, which select dependency-relevant preceding statements as context for instantiation and repair. Second, AQT records the cumulative schema context of the source test case, and \tool{} maintains the corresponding target-side context, updating it after each translated statement. Third, abstract labels separate dialect-specific constructs from the surrounding structure, so that dialect-aware instantiation remains local while the structure is preserved. Finally, \tool{} uses parser and execution feedback to repair transferred seeds before mutation. We have updated Table~I and Sections~II (Background and Motivation) and~VI (Related Work) to reflect these differences.

\textbf{Different results.} These differences lead to different results in Section~IV (Evaluation). For translation, \tool{} improves execution validity by 130\% over \sedar{}, while SQLGlot, CrackSQL, and RISE reach at most 0.314 on DuckDB, compared with 0.748 for \tool{}. On the sampled MySQL-to-DuckDB test cases, \tool{} also achieves the highest result and state equivalence (52.0\% and 74.0\%, compared with 38.0\% and 69.0\% for \sedar{}). Disabling cross-statement context propagation reduces execution validity from 0.716 to 0.523, and replacing dependency-based context selection with a recency-based window or the full context reduces it to 0.599 and 0.643, respectively. For fuzzing, \tool{} covers 14\% more branches and detects 16 more bugs than \sedar{}. On DuckDB, it covers 33.6\% and 16.7\% more branches than SQLGlot+\griffin{} and RISE+\griffin{}, respectively, and detects 3 more bugs than each. With the same seeds, \tool{}'s mutation handling achieves 4.0\%--27.2\% higher coverage than that of \sedar{}.

% Source: Reviewer A, Question 2.
\reviewquestion{1.2} What independent benefit does the dependency graph provide beyond context propagation?

\reply
The dependency graph guides context selection during instantiation and repair. Without it, \tool{} lacks explicit links for selecting dependency-relevant statements and object-state summaries for prompting. For example, in \texttt{ALTER TABLE t ADD COLUMN b INT; SELECT b FROM t;}, the edge selects the schema update for the translation and repair of the \texttt{SELECT}. Summaries provide the content, while edges guide the selection.

To isolate this benefit, we have added an ablation study in Section~IV (Evaluation). We compare four context-selection modes under the same LLM, knowledge base, source corpus, repair budget, and statement order: (1) \tool{}, which selects predecessors through the dependency graph; (2) $\tool{}_{\textit{win}}$, which replaces dependency-based selection with the five most recent successfully translated statements while keeping the same object summaries, so that it differs from \tool{} only in whether the dependency graph is used; (3) $\tool{}_{\textit{all}}$, which provides all preceding successfully translated statements together with the complete source-side and target-side context; and (4) $\tool{}_{\textit{w/o-ctx}}$, which disables target-side context propagation. We measure execution validity at the statement level, the number of predecessor statements provided per statement, the proportion of provided predecessors that are dependency-relevant (i.e., connected to the current statement by a dependency edge), and input tokens per statement.

As shown in the table, \tool{} achieves higher execution validity than $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$ (0.716 vs. 0.599 and 0.643), while reducing input tokens per statement by 11.9\% and 72.3\%, respectively. In $\tool{}_{\textit{win}}$ and $\tool{}_{\textit{all}}$, only 22.6\% and 4.2\% of the provided predecessors are dependency-relevant. In addition, 15.4\% of statements select dependency predecessors outside the five most recent statements, which a recency-based window cannot capture. The context of $\tool{}_{\textit{all}}$ grows with test-case length: on test cases with more than 20 statements, its input tokens per statement are 4.98$\times$ those of \tool{}. These results show that the independent benefit of the dependency graph lies in selecting a compact, dependency-relevant context whose size does not grow with test-case length, while achieving higher execution validity than larger contexts.

% Source: Reviewer A, Question 3.
\reviewquestion{1.3} How were CrackSQL, RISE, and SEDAR adapted and configured for the four target DBMSs, and how did the authors ensure a fair comparison?

\reply
We have added the configuration of the translation baselines in Section~IV (Evaluation), and the number of initial seeds used for each target DBMS in the experimental setup. Each baseline follows its original translation workflow. SQLGlot and jOOQ use their built-in dialect support; CrackSQL and RISE use the official SQL documentation of each target DBMS as dialect knowledge, while \sedar{} requires no additional dialect knowledge. Since CrackSQL and RISE are designed to translate one query or artifact at a time, we translate the statements of each test case individually and reassemble them in their original order, without schema context. \sedar{} translates complete test cases using the extracted source schemas as context.

To ensure a fair comparison, all methods transfer the same collected test files and use the same number of initial seeds for each target DBMS (5,879, 4,551, 5,850, and 5,990 for MonetDB, Virtuoso, DuckDB, and ClickHouse, respectively). No method receives additional manually written translation rules. The prompts and configurations used by all baselines are included in our artifact.
